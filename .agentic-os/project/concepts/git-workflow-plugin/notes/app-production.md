# Production GitHub App for PLAN-plugin T6.1

The App that releases, promotes and applies rulesets for the real repositories, checked on 2026-11-10. It holds no secret: the private key stays a read-only file on the developer machine and is named in no repository, and no token was written anywhere.

## App

- Name `git-workflow-app`, owned by the organisation `edotz`, installable only on that account (the name `git-workflow` was entered first; the registered App carries the slug `git-workflow-app`). App ID 5694393, which is the value of `GIT_WORKFLOW_APP_ID` in the `.env` of every repository that runs rules-sync.
- Installation 180463371 on the organisation, repository selection `selected`, not suspended, no events subscribed, no webhook.
- Permissions, read back through the organisation installations endpoint: administration write, contents write, pull requests write, metadata read. Packages write is not granted: an App token cannot publish organisation packages (verify-github.md row L467) and no command asks for it. Workflows write is not granted either; the first baseline force push of a child repository decides whether it is needed (PLAN-plugin T5.5).
- Repositories of the installation, confirmed by one token each: `edotz/typo3-cms` (working copy edotz.typo3-cms), `edotz/php-project` (edotz.php-project), `edotz/nodejs-project` (edotz.nodejs-project) and `edotz/git-workflow` (this repository). Child repositories that receive a split are added when their baseline is planned.
- Key: generated by an organisation owner, mode 600 in `~/.ssh`, outside every repository, no backup (decision D16 of PLAN-plugin). A lost key is replaced by generating a new one and deleting the old one.
- Token service: the container of `docker-compose.yaml` on `127.0.0.1:8790` for the organisation `edotz`, with the production key mounted read-only and `TOKEN_SERVICE_APP_ID` 5694393. The container of the sandbox App was stopped and removed before. The developer authenticates to the service with the `gh` login (organisation membership, decision D48).

## Result

- A token for the production App was obtained through the token service for each of the four repositories, with the permission sets `contents` and `administration`. Each token is an installation token, narrowed by the service to the one repository it was asked for: the installation endpoint, called with a `contents` token for `edotz/git-workflow`, listed that repository only.
- With the installation token exported the token reads `edotz/typo3-cms`, `edotz/php-project`, `edotz/nodejs-project` and `edotz/git-workflow` (default branch `master` in all four). A repository outside the installation, `edotz/logger`, is refused by the service with "repository not installed (HTTP 404)".
- The `administration` token reads the rulesets of the four repositories: none has a ruleset yet. Each has classic branch protection on `master` with required status checks (typo3-cms 2, php-project 2, nodejs-project 1, git-workflow 2), a mechanism apart from rulesets that rules-sync leaves in place (the pilot of the daily loop found the same with an old ruleset); whether it blocks a push of the App was not tested here, and each migration decides whether to remove it (T6.2 names it, T6.3, T6.5 and T6.6 act on it).
- Bypass: the App becomes the bypass actor of the rulesets when rules-sync creates them with `GIT_WORKFLOW_APP_ID`. Nothing has been created in these repositories yet, so the bypass is not checked here; the first migration (T6.3) does.
- No key, no token and no key path is recorded in this note.
