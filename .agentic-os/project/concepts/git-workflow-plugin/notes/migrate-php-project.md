# Migration of edotz/php-project for PLAN-plugin T6.5

`edotz/php-project`, the monorepo of eight private Composer packages, moved from the old child-release train (release-please in each child, backport commits into the monorepo, `merge-split-repo.yml`) to the git-workflow plugin on 2026-11-11. The production App `git-workflow-app` made every change on GitHub that is not a pull request, the developer merged the pull requests, and the developer's login prepared the children. No key or token was written to a file.

## Repository

- Roles (D79, D80): `master` is the development branch, `2.x` the release branch and `1.x` the legacy line.
- Project tier: `17bf694 chore(project): setup of agentic-os`, committed by the developer directly on master before the migration.
- Pull request #70 (squash merge `04ab447`): `components.yaml` with eight components `collection`, `db`, `error`, `log`, `object`, `persistence`, `serializer` and `utility`, each with path `packages/<name>`, version file `packages/<name>/composer.json`, `split: yes`, owner `edotz`, repo `php-<name>` and a php-cs-fixer check of its own path; `status-checks.yml` copied from the plugin (commit lint, the pull request title step, `setup-php` with php-cs-fixer, the checks of `components.yaml`); `commit-lint.yml`, `php-cs-fixer.yml` and `merge-split-repo.yml` removed. The new `check` job passed on the pull request, which was the first run of the title step on a runner.
- Rulesets of the production stage, created by `rules-sync --apply`: `master`, `release` (`2.x`) and `legacy` (`1.x`). `rules-sync` named the classic protection of master with its required checks `Validate Conventional Commits` and `PHP-CS-Fixer` and left it; the classic protection of master, `1.x` and `2.x` was removed through the API with the login of the developer only after the three rulesets existed, so no branch was unprotected (`Branch not protected` for all three).
- Legacy line: the head of `1.x` is tagged `legacy/1.x-freeze` (`753f32d`, pushed first); pull request #71 (squash merge `57093f4`) removed 47 files from `1.x`: the old workflows, `branch-protection.yaml`, and the release-please files and workflows that each package directory carried; the tree of `1.x` holds none of them. `legacy/1.x-cutoff` of the old approach stays.
- Baseline tags of the monorepo: one lightweight tag per component on the last commit that touched its directory, which is the `chore(backport): sync release vX` commit of that package (`collection/v2.0.0`, `object/v2.0.0`, `serializer/v2.0.0` and `utility/v2.0.0` on `bf9406f`, `db/v2.0.1` on `a3b0379`, `error/v2.0.2` on `c7aa855`, `log/v2.0.3` on `ca1a93c`, `persistence/v2.0.2` on `aec1281`), pushed to GitHub.
- Children: `php-collection`, `php-db`, `php-error`, `php-log`, `php-object`, `php-persistence`, `php-serializer` and `php-utility`, private, with the branches `1.x` and `2.x` (`php-db` only `2.x`), the default branch `1.x` (`2.x` for `php-db`) and the tags `v2.0.x` of the old approach. The developer added them to the installation of the App. The developer's login created `master` at the `2.x` head of each child and set it as the default branch, because the split refuses a child whose default branch is not the main branch of the monorepo (D74).
- Settings for the `.env` of php-project, to be written by the developer: `GIT_WORKFLOW_RELEASE_BRANCH=2.x` and `GIT_WORKFLOW_LEGACY_BRANCHES=1.x`; every command of the migration ran with them as environment overrides, because the shell of the session exports its own values over the `.env`.
- The shims of the clone (`pre-commit`, `commit-msg`, `pre-push`) were current (`app git shims --check`), so the pre-push guard runs the minimum check before every push.

## Result

- Split dry run for every child: the old head is not an ancestor of the split head ("histories diverged") and the tree difference is none, so the split of master has the content of the `2.x` head of each child and only the history is replaced.
- Baseline apply, one child per run with `--confirm edotz/php-<name>` after the developer confirmed `php-collection` first and then the other seven: the old head of each child is tagged `legacy/pre-split` (the same commit as its `2.x`), `master` is replaced by the split head with a lease ("forced update"), and the component tag is not pushed because `v2.0.x` already exists on the old commit: the apply prints the warning "skipped" and moves nothing (D83). The second apply of `php-collection` printed "nothing to apply". After the eight runs `master` of the children is at `6b09192`, `0abc831`, `36fd87c`, `26248c7`, `786dce4`, `d4bf7b8`, `50c083e` and `76ec50f`; `2.x`, `1.x` and every old tag are unchanged.
- Release: `app git release --dry-run` answers "Nothing to release: no component changed since its latest tag", because the only commit after the baselines is the migration commit, which touches no package. So no component release was made and no GitHub Release was created; the release command makes GitHub Releases with `--latest=false`, and the first release of a package pushes its tag to the child through the split.
- Baseline of `2.x`: the release branch keeps its old content and its old workflows until the first real release of a component; the one-time move to the release commit (tag `legacy/pre-promote`, force push with a lease) needs the baseline mode of `git promote` (D81).

## Defects the migration found

- git-cliff drops a tag on a commit that does not touch the component path when it filters with `--include-path`: the first baseline tags, placed on the commit of the project tier, made every component count its whole history as unreleased and the dry run proposed `3.0.0` for all eight. A baseline tag has to sit on a commit that touches the component directory; here the last commit of each package was its release state. A fix in the plugin (a commit range instead of the tag search) is an open amend.
- The split refuses a child whose default branch is not the main branch of the monorepo; all eight children had `1.x` or `2.x`, so `master` had to be created and made the default first.
- A tag of the child at another commit stopped the apply with "it is not moved"; D83 turned that into a warning and T6.14 changed `split.sh`.
- The tool image runs no git inside a linked worktree (its git directory lies outside the mount): `app git split` fails there with "splitsh-lite failed"; the dry run worked from a real clone and from the main copy.
- The local baseline tags were set back to the wrong commit once by a fetch outside the session, after the first correction; the remote tags were corrected with a forced update and the local ones set again.

## Cleanup of the old release train in the packages

Found after the baselines, on the question of obsolete files: master of php-project still carried 49 files of the old child release train, `release-pipeline.yml` (release-please), `sync-to-monorepo.yml` (the backport), `release-please-config.json`, `.release-please-manifest.json`, `.github/branch-protection.yaml` of every package, the `.github/CLAUDE.md` that documents it, and `.github/README.md` and `.github/branch-protection.yaml` of the root. My first version of this note and the verify of T6.5 looked only at the root workflows, so the baseline had already copied those files into the `master` of the eight children; the child workflows trigger on `2.x` and the split never pushes there, so they stayed dormant.

- Pull request #72 (squash merge `6f6acc4`, title `ci: remove the old release train of the packages`) removed the 49 files; `status-checks.yml` is the only file left under `.github`.
- Because a `ci:` commit that touches a package directory after its baseline tag makes git-cliff propose a patch release (checked: `logger/v1.0.1` plus the cleanup commits gave `logger/v1.0.2` in the sister repository), the eight baseline tags were moved once more with a forced update, to the squash commit `6f6acc4`, and the release dry run lists every component as "tag is HEAD" with no bump.
- Split apply per child after the cleanup: a fast-forward of `master` (no force, no `legacy/pre-split` change), `master` of the children is now at `3a7501f`, `3fd8304`, `7fbfa7b`, `7584d3f`, `8f2940d`, `f2ce627`, `d9a39f5` and `2a1a80d`; none of them holds a release-please, branch-protection, release-pipeline or sync-to-monorepo file; `legacy/pre-split` and `2.x` of the children are unchanged.
