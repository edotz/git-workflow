# Pilot release in the sandbox for PLAN-plugin T3.8

A pilot single repository released and promoted with `app git release` and `app git promote`, run on 2026-11-04. It holds no secret: the private key of the App stays on the developer machine and no token was written to a file.

## Repository

- Repository: `edotz/git-workflow-sandbox`, private, working copy `/home/ohoeft/worktrees/git-workflow-sandbox`, branch `master`.
- Setup by pull request #5 (squash merge `8e2cf3d`): `components.yaml` with one component `sandbox` at the root (`paths: ["."]`, `version_files: [package.json]`), `package.json` at version 0.0.0, the README markers `<!-- release:start -->` and `<!-- release:end -->`, `.gitignore`, and `.agentic-os/project.yaml` that names the plugin. The local `.env` holds `MAIN_BRANCH=master` and `RELEASE_BRANCH=release`.
- Baseline: the tag `v0.0.0` on `8e2cf3d`, because the first commit of the sandbox is not conventional and the minimum check lints every commit since the latest tag.
- Change to release: pull request #6, `feat(sandbox): add a greeting` (squash merge `c6680eb`).
- Token service: the container of `docker-compose.yaml` on `127.0.0.1:8790` with the key of the sandbox App (App ID 5593711) mounted read-only.
- The developer login came from the exported `GH_TOKEN` of the shell, because `gh` has no stored login on this machine.

## Result

- Dry run: version 0.1.0, tag `v0.1.0`, files `package.json`, `CHANGELOG.md` and `README.md`, notes with the one feature. The working tree stayed clean.
- Apply: release commit `88fefb4` `chore(sandbox): release v0.1.0` on `master`, tag `v0.1.0` on it, both pushed with the installation token of the App; the push passed the ruleset through the bypass of the App ("Bypassed rule violations", pull request and required check). `package.json` holds 0.1.0, `CHANGELOG.md` holds the 0.1.0 section, the README lines between the markers read `Version 0.1.0` and a release link.
- GitHub Release: `v0.1.0`, id 433832351, created by `git-workflow-sandbox[bot]` (type Bot), not a draft, not a pre-release, target `master`.
- Repeated apply: nothing new. The push said "Everything up-to-date", the output said the GitHub Release exists, and the count of releases stayed at 11.
- Promote: the dry run named commit `88fefb4`; the apply created the branch `release` at that commit (it did not exist before) and a second apply said the branch is at the tag already.
- The commit author is the developer (`Olaf Hoeft`); GitHub shows it as not verified, because the commit is not signed.

## Second cycle: v0.2.0

- Pull request #7, `feat(sandbox): add a farewell` (squash merge `c1cbf37`), then `release --apply` on `master` with the hook of the clone still installed.
- The commit passed without the repository hooks (release commit `0611b67`, tag `v0.2.0`). The push then failed with "Could not resolve host: github.com" from the tool container, a network loss on this machine, and left the commit and the tag local with a clean tree.
- The rerun found the tag `v0.2.0` on HEAD as pending, pushed `master` and the tag, and created the GitHub Release `v0.2.0` by `git-workflow-sandbox[bot]`. Its body is the feature section of the tag, 112 characters, without the release commit.
- The promote dry run named `0611b67` and the apply moved the branch `release` from `88fefb4` to `0611b67`: a real fast-forward. `master` and `release` both point at `0611b67`.
- Git-cliff proposed 0.2.0 for one `feat` after 0.1.0: in a 0.x version it bumps the minor number.

## Defects the pilot found

- The first apply stopped at the release commit: the hook `.git/hooks/pre-commit` of the clone (installed from the git template of the framework) runs `exec agentic-os`, which is not in the tool image. The command left its files staged. Fixed: the release commit runs without the repository hooks and a failed commit restores the files (decision of the developer, 2026-11-04).
- The GitHub Release body of `v0.1.0` holds only the line `<!-- generated by git-cliff -->`: the notes were read with `--unreleased` after the tag existed, so git-cliff found nothing. Fixed in `release.sh`: the notes of the publish step are read from the existing tag without its own release commit. The second release `v0.2.0` shows the fix: its Release body holds the feature "Add a farewell" and no release commit.
- The process environment of the shell exports `RELEASE_BRANCH=0.x`, which wins over the `.env` of the project, so the first promote dry run named the branch `0.x`. The pilot ran with `RELEASE_BRANCH=release` set on the command line.
- The framework writes `.agentic-os/plugins.json` and `.agentic-os/plugins.env` into the project; the sandbox has no `.agentic-os/.gitignore` for them, so the first apply refused a dirty tree. They are excluded in the local `.git/info/exclude` of the clone.
